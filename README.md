# buchnative — счетоводна програма

Счетоводна програма за българския пазар: фактури, контрагенти, сметкоплан,
счетоводен дневник (дебит/кредит), публикуване на фактури, мултитенант (активна
фирма), светла/тъмна тема и български/английски интерфейс.

**Сайт:** [buhal.sbs](https://buhal.sbs) (GitHub Pages) — Бухалът не спи през
нощта: документи, счетоводство и код на езика Baga върху нативна база rocksbaga.

Изградена по образец на референтната програма в `secret/` (локално, не се качва
в git).

**Документация (текущо състояние на кода):** виж [`docs/`](docs/README.md) —
архитектура, модули, документи/обекти, API, конвенции и какво още липсва.
`PLAN.md` е пътната карта (прототип + следващото). Не е истината за всеки ред
от кода — за това е [`docs/`](docs/README.md).

## Контекст

2026 година е. България е в еврозоната — основната валута на счетоводството е
**евро (EUR)**. Чуждите валути се преизчисляват по официалните обменни курсове
на Европейската централна банка (ЕЦБ), импортирани от фида
`eurofxref` (дневен / 90-дневна история).

## Архитектура

**Приложенията остават универсални** — fmrbaga, ormbaga и останалите пакети от
`app-product/` не се копират и не се променят. buchnative ги използва както са:

- **компилация** — чрез path-зависимости в `backend/sandak.toml` (baga монорепото)
- **работа (runtime)** — само през портове, по стандартните протоколи; никакви
  специални мостове или вграждане

| Услуга | Порт | Протокол |
|--------|------|----------|
| rocksbaga | 16579 | RESP2 (`tools/serve.baga`) |
| backend API | 8080 | HTTP/JSON (fmrbaga) |
| frontend (dev) | 3000 | HTTP (Next.js) |

## Стек

| Слой | Технология |
|------|-----------|
| Backend | Baga + fmrbaga framework (HTTP/JSON, route-id dispatch, OpenAPI, JWT) |
| База данни | **rocksbaga** — дълготраен LSM KV, RESP2, през `drockb`; `ORM_BACKEND=drock` в ormbaga |
| Frontend | Next.js (App Router, React 19, чист CSS) |
| Автентикация | JWT (jwtbaga HS256) |

Базата е сменена спрямо bagabuch: rocksbaga е един писател върху LSM, без
SQL engine и без нишки, които се състезават. boilaDB държи стотици такива —
за сонда на езика е добре, за счетоводно приложение значи забиване.
Редовете са JSON по ключ (`kv:t:<таблица>:<id>`); как работи слоят — виж
[docs/conventions.md](docs/conventions.md#kv-слоят-как-работи).

## Функции

- **Фирми, Сметкоплан (йерархия), Контрагенти, Стоки и услуги** — CRUD;
  контрагент от VIES; адресът се дели към SAF-T полета ако фирмата има
  Mistral ключ (Настройки → Интеграции; [docs/ai.md](docs/ai.md));
  сканиране на фактури към чернова с редове (`/scan`: Mistral OCR или UBL Peppol)
- **Фактури** — пълна форма като в inv: тип (фактура/проформа/кредитно/дебитно),
  автоматичен номер, данъчно събитие, контрагент и артикули с търсене, мерки,
  ДДС по ред (20 / 9 / 0 / освободени), отстъпка, цени с/без ДДС; печат
  (оригинал/копие) и експорт PDF/DOCX/ODT през reportbaga (`0000000078_invoice.pdf`);
  справки PDF/XLSX/ODS като таблица през същия път (`/reports`)
- **Публикуване на фактура** — генерира счетоводни записи по типови кореспонденции
  (изходяща: Дт 411 / Кт 702 + Кт 4532; входяща: Дт 602 + Дт 4531 / Кт 401);
  балансът дебит = кредит се пази; втори пост → 409. Кредитно известие ползва
  **същите** сметки със **отрицателни** суми — статиите не се обръщат.
- **Счетоводен дневник** — дебит/кредит редове по запис. **Отрицателният знак е
  позволен** във формуляра и се записва така в базата (сторно, кредитно известие,
  погасяване на аванс, корекция). Група 60 се води с чисти обороти: минус по
  дебита намалява оборота, не се прави насрещна статия. Σ дебит = Σ кредит
  остава (и двете страни могат да са отрицателни заедно).
- **ДДС** — дневници покупки/продажби, клетки ППДДС 01-01…01-82, ZIP/TXT за
  НАП (DEKLAR/POKUPKI/PRODAGBI в Windows-1251); минусът е позволен при кредитно
  известие и корекция на грешка и отива в клетките и файловете за НАП
- **Банки** — сметки (IBAN, ГЛ + буфер), импорт на извлечения (OBB XML,
  camt.053, PostBank XML, MT-940, CSV), осчетоводяване и разнасяне
- **Дивиденти** — разпределение към действителни собственици, данък 5% ЗДДФЛ
- **Производство** — рецепти (BOM) и поръчки; confirm изписва материали,
  заприходява продукция и прави запис 611
- **Справки** — оборотна ведомост, главна книга, главна книга по кореспонденции
  (водещ дебит и водещ кредит), баланс / ОПР / паричен поток / собствен капитал
  (формули в Настройки), хронологичен журнал, по контрагент; екран `/reports`;
  експорт PDF/Excel/ODS като таблица през reportbaga (като фактурите). Как се
  настройват отчетите: [docs/financial-statements.md](docs/financial-statements.md)
- **Валутни курсове (ЕЦБ)** — импорт на официалните курсове на Европейската
  централна банка от `eurofxref` фида (дневен / 90-дневна история), справка по
  дата с отстъпка към предходен работен ден, автодовършване на курса във
  фактура в чужда валута; TLS към ЕЦБ с котвен сертификат Sectigo OV E36
  (презаписваем с `BUCHNATIVE_ECB_ANCHOR_FILE`)
- **Вход** — email + парола; JWT през jwtbaga (`fmr_issue_token`). Правата по
  роля (baraba: super_admin / admin / accountant / viewer) се налагат върху API.
  Дефолт: `superadmin` / `123+123`.
- **Мултитенант** — активна фирма по потребител; `company_id` на фактури,
  дневник, стоки и контрагенти (плюс банки, дивиденти, производство)
- **Светла/тъмна тема** — глобално от самото начало, запазва се, без проблясък
- **Български (дефолт) + английски** — речници в `frontend/lib/i18n.ts`, запазват се
- **Частичен PATCH** — обновяват се само подадените полета (не се трият данни)
- **Числови низове в TEXT колони** (ЕИК, фактурни номера с водещи нули) — работят

## Защо Mistral за AI (скан и адрес)

Фактурата е финансова информация. ЕС не позволява такава информация да се
изнася към трети страни — затова не ползваме американски или китайски облак
за OCR, дори да е евтин.

- **Mistral** е европейски (Франция). Ключът е по фирма. OCR 4.1 + Small 4 е
  евтиният път, който на практика чете български фактури към чернова с редове.
- **Google / Azure** имат центрове в ЕС (данните могат да останат тук), но
  са скъпи за същата работа. Остават резерва, не първи избор.
- **Китайски AI** (напр. Zhipu/GLM) спазва закона: всеки опит за сканиране
  на фактура се отхвърля. Полето за ключ в настройките стои, но не е път
  за покупки/продажби.

Подробности и как се пробва: [docs/ai.md](docs/ai.md).

## Изисквания

- **Baga** — buchnative живее в baga монорепото (`app-product/buchnative` е
  submodule). `scripts/dev.sh` намира корена на монорепото сам (две нива нагоре).
- **Node ≥ 20** (препоръчително 22 през nvm — `dev.sh` го добавя към PATH)

## Стартиране

```bash
./scripts/dev.sh     # цял стек (Ctrl+C в същия терминал също спира)
./scripts/stop.sh    # спира стека и от друг терминал
./scripts/seed.sh    # демо данни (след като backend е на :8080)
```

Стартира трите услуги на техните портове (rocksbaga → backend → frontend).
Отвори `http://localhost:3000`. За разработка: изтрий `db/` (пази
`.gitignore` — това е `LSMPATH` на rocksbaga), пусни `dev.sh`, после
`./scripts/seed.sh` — фирма Бага ООД,
сметкоплан, контрагенти, фактури.
Вход: **`superadmin` / `123+123`**.

Портовете и настройките се задават само чрез env променливи (виж
`backend/.env.example`); нищо не е хардкоднато.

## Структура

```
buchnative/
├── backend/               # Baga приложение върху fmrbaga
│   ├── sandak.toml        # path deps → fmrbaga, ormbaga, drockb, std
│   ├── start.baga         # проверка на връзката → fmr_run
│   ├── routes.baga        # route table + dispatch (стабилни route id-та)
│   ├── schema*.baga       # само справка за колоните (KV е безсхематичен)
│   ├── actions/           # handlers по модул
│   └── models/            # table helpers
├── frontend/              # Next.js
│   ├── app/               # страници (login, фирми, сметкоплан, …)
│   ├── components/        # провайдери (тема/език/автентикация), обвивка, CRUD
│   └── lib/               # api клиент, i18n речници, storage
├── scripts/dev.sh         # локален старт на трите услуги
├── PLAN.md                # план и пътна карта
├── sstart.md              # начална задача
└── secret/                # (gitignored) референтната програма — само образец
```

## API (основно)

Всичко под `/v1/...`, JSON, JWT Bearer. Пълният списък е в
[`docs/api.md`](docs/api.md). Накратко: фирми и настройки (обекти, кочани),
сметкоплан, контрагенти, продукти, фактури (+ пост/печат/UBL), вътрешни
документи (+ confirm без дневник), производство (рецепти + поръчки + confirm
с дневник), дневник, ДДС (+ файлове за НАП), банки, дивиденти, SAF-T, ДМА,
курсове, потребители и роли.

## Git

buchnative е **отделно репозиторий** (`github.com:bagalang/buchnative`), регистрирано
като submodule в baga монорепото (`app-product/buchnative`). `secret/` никога не се
качва.

По пътя бяха фиксирани три универсални бъга в общите пакети (не тук):
- boilaDB `8f68e3b` — unknown-literal коерция str↔i64/num (числови низове в TEXT)
- ormbaga `a2e68b0` — multi-column UPDATE (презаписваше SET списъка)
- boilaDB `c7d5fbb` — числови низове с водещи нули вече не се инференцират като числа

Миграциите от bagabuch (`schema_pg_*`) **не се прилагат** върху rocksbaga —
KV е безсхематичен, а `ORM_BACKEND=drock` ги пропуска в `start.baga`. Остават
в дървото само като справка за колоните и техните по подразбиране стойности.
Историческия boilaDB набор (`schema_boila_*`) е премахнат — buchnative не се
използва с boilaDB.

Жив файлов архив от админа: `BACKUP` checkpoint на rocksbaga → споделен обем → S3.
Физическият checkpoint е операция на сървъра (`CHECKPOINT` / `BACKUP` през
drockb) — не замества логическия dump.
