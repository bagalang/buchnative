# Конвенции, които чупят нещата ако се забравят

## Filesize gate 600

`.baga` файл над ~600 реда не минава. Затова и ormbaga KV слоят е разцепен
(`session/db.baga`, `result.baga`, `kv_row.baga`, `kv.baga`, `kv_write.baga`),
а големите action файлове се цепят
(`fixed_assets` / `fixed_assets_ops`, `internal_docs` / `internal_docs_confirm`,
`invoices` / `invoices_update` / `invoices_post` / `invoices_print`,
`reports` / `reports_util` / `reports_trial` / `reports_book` /
`reports_corr` / `reports_fs`,
`recipes` / `production` / `production_confirm`,
`dividends` / `dividends_ops`, `vat` / `vat_files` / `vat_line` / `vat_fmt`,
`bank_accounts` / `bank_transactions` / `bank_transactions_ops` / `bank_parse`).

Преди да надуеш файл — `wc -l`. `invoices.baga` вече е на ръба.

## KV слоят (как работи)

Базата е **rocksbaga** (KV, RESP2) през `drockb`; `ORM_BACKEND=drock` включва
KV backend-а в `ormbaga`. SQL няма — редът е JSON под ключ
`kv:t:<таблица>:<id:012d>`, колоните са ключовете му.

**Защо action файловете не се пипат.** `PgRows` е обикновена структура, затова
`kv_select_*` попълва **същия `OrmQuery`**, който `orm_cell_by` / `orm_nrows` /
`orm_db_q` четат — accessor-ите не отличават backend-а. Това важи и за общия
table API (`orm_insert_returning_full`, `orm_update_by_id`,
`orm_delete_by_id`, `orm_count_sql`, `orm_find_i64`, `orm_where_eq_str`):
всеки има KV път в `ormbaga/session/orm.baga`.

**Как се мигрира модел.** Погледни `models/account.baga` като шаблон:

| SQL версия | KV версия |
|---|---|
| `X_select_sql()` (SELECT списък) | `X_cols()` — ред от `vec_push` |
| `orm_query_params(db, sql WHERE id=$1, …)` | `kv_select_by_id(db, табл, id, cols)` |
| `orm_query_params(db, sql WHERE col=$1, …)` | `kv_where_star(db, табл, col, val)` или `kv_select_where` |
| `orm_query(db, sql ORDER BY x)` | `kv_select_all_order(db, табл, x, cols)` |
| `orm_insert_returning_full(…)` | `kv_insert(…)` (id се раздава от брояча) |
| `account_to_json(q, row)` | **непроменено** |

Вторичният индекс се поддържа за всяка колона, значи `WHERE col = val` е GET,
не скан. `created_at` се щампова в модела (`kvtime.baga`) — в KV няма
`DEFAULT NOW()`.

**Суров SQL е грешка, не празен резултат.** `orm_query_params` върху drock
връща ясна грешка и **не пипа db**. Това е нарочно: `orm_query_from` строи
`OrmDb` от `PgResult` с `backend=PG` и мъртъв `kv`, значи предишното
поведение подменяше живата връзка на работника и целият му worker после даваше
503. Ако модел още не е мигриран, виждаш точно кой SQL липсва.

**Транзакции няма.** `bb_begin` / `bb_commit` / `act_err_rb` са SQL-семантика;
върху KV те са no-op или грешка. Проводка на фактура се прави с един `MSET`
(ред + индекси + салда са атомарни спрямо читателите); ако трябва повече —
виж `ormbaga/session/kv_write.baga`, не въвеждай имитация на SQL транзакция.

## Числа

Пари и количества са стрингове през целия стек (`bagadecimal`). Не слагай
float в JSON. ЕИК и фактурни номера с водещи нули са TEXT — не ги пращай
като числа. **Отрицателният знак е валидни данни** в дневник, фактура и
ДДС дневници (кредитно известие, сторно, погасяване на аванс, корекция).
Не слагай `CHECK (amount >= 0)` и не отхвърляй минус в API. Не обръщай
дебит↔кредит при сторно — виж `PLAN.md`.

## Триене и редакция (свободно)

Това е счетоводна, не складова програма, и реалността е: документите
идват със закъснение, въвеждат се ръчно, без баркод четец и без ежедневна
каса. Затова грешките при въвеждане са чести и **триенето и редакцията са
свободни** — няма заключване по статус и няма проверка за затворен период
при корекция на вече въведен документ.

- „Върни към чернова" и „Изтрий" махат записа в дневника **изцяло**
  (редове + заглавен ред), а при входяща фактура връщат и партидата в
  склада. Целта е чисти обороти по 60/70, а не изкуствени обратни статии.
- Корекциите на вече приключен период не се правят със сторно, а с
  кредитни известия и отрицателни суми (виж по-горе).
- Партида, която вече е частично изписана, не се връща автоматично —
  операцията отказва с ясно съобщение, за да не се измисли наличност.
  Изходяща фактура връща количеството като нова партида по текущата
  средна себестойност (количеството е точно, оценката — приблизителна).
- Груповите действия (`/v1/invoices/bulk/{post,unpost,delete}`) приемат
  `{"ids":[...]}` и връщат `{posted|unposted|deleted, failed, results}` —
  всеки документ е в своя транзакция, един провал не блокира останалите.

Excel/ODS през officebaga: клетката е **число** (`t="n"` / `office:value-type="float"`),
XML стойността е с точка. Excel и Google Sheets я показват със запетая при
български локал. Номера с водещи нули остават текст. В HTML на справката
сумите са със запетая (`rpt_bg_num`).

## Дати (`chronobaga`)

Съхранение и JSON са само ISO `YYYY-MM-DD` или финансов `YYYYMMDD`.
ДДС период / счетоводен месец е ISO `YYYY-MM`. Печат на фактура и ДДС
дневник на екрана са български `dd.mm.yyyy` (`dt_to_bg` / `formatBgDate`).
Не пиши `30/08/2026` и не гадай locale. OCR на фактура: `dt_parse_invoice`,
после пак ISO в базата.

Baga `<` `>` `<=` `>=` върху `str` сравняват **указатели**, не текста.
`==` / `!=` са стойностни. За ISO дати в справки ползвай `xml_str_lt`
(`rpt_in_range`). Иначе оборотната ведомост излиза празна при пълни записи.

## Route id

Стабилни цели числа в `routes.baga`. Нова група взима празен диапазон
(не размествай старите). `GET …/next-number` преди `GET …/{id}`.

## UI

- български е дефолт, английски втори; ключовете са в `frontend/lib/i18n.ts`
  (и двата речника)
- тема светла/тъмна от самото начало
- частичен PATCH: липсващо поле = не пипай, не нулирай
- **търсачка** в списъците (клиентски филтър върху заредените редове) —
  `CrudPage` (фирми, сметкоплан, контрагенти), стоки, дневник, вътрешни
  документи, начални салда, фактури, банкови сметки, производство, дивиденти
- **икон-бутони** за ред в таблица/списък: молив = редакция, кошче = изтрий,
  око/печат/активирай/история — `frontend/components/IconButton.tsx`,
  клас `.btn-icon` + `.icon-actions`. `title` / `aria-label` носят текста
  (подсказка при посочване)
- основните действия остават с надпис: Създай, Запази, Осчетоводи, Потвърди

## TLS към външни HTTPS

Котва = **прекият издател**, не root. Хардкодната в кода; override:
`BUCHNATIVE_VIES_ANCHOR_FILE`, `BUCHNATIVE_ECB_ANCHOR_FILE`,
`BUCHNATIVE_MISTRAL_ANCHOR_FILE`. Виж [architecture.md](architecture.md).

## Регистрация, парола, 2FA

Публичната регистрация създава потребител **и** фирма веднага (без email
потвърждение — за разлика от baraba). Спира се с `auth.registration_enabled=0`
в глобалните настройки. Възстановяване на парола е SMTP sidecar +
`app.url` (линк `/reset-password?token=`). 2FA е `otpbaga` (TOTP + hashed
резервни кодове); MFA JWT има `"mfa":1` и не минава към останалите пътища.

## SMTP и S3

Не се пишат Baga пакети за поща и object storage. Същото като su-doxis:
Python sidecar `scripts/py/sidecar.py` на `:5050` (Flask + boto3). Backend-ът
говори HTTP (`BUCHNATIVE_SIDECAR`). `dev.sh` го пуска.

S3 архивът е **логически dump**: обхождат се редовете и се събират като JSON.
Не се тарват файловете под `LSMPATH` — това не е snapshot, докато сървърът
пише. rocksbaga има свой физически checkpoint (`CHECKPOINT` / `BACKUP` през
drockb, виж `app-product/drockb`), но той е офлайн/сървърна операция, не
алтернатива на логическия dump за архив.

**Известна дупка:** `scripts/py/dump.py` (Python sidecar) още говори PG wire
и прави `COPY TO STDOUT` — това е оцелял код от boilaDB епохата и трябва да
смени на обхождане на KV редовете. `dev.sh` вече му подава `LSMPATH` /
`DROCK_PORT`, а не PG env — значи самият скрипт е следващата стъпка.

## SAF-T номенклатури

Официалните кодове на НАП (движения, фактури, данъци, области, сметки)
са **каталог в кода**, не таблица. Същото като мерки и основания за 0% ДДС.
Не ги правим CRUD — подаването към НАП иска точно тези кодове.

Дт/Кт кореспонденциите към тези кодове (`saft_account_mappings`) **са**
настройка по фирма: CRUD на `/saft-movement-mappings`. Паричните типове
(каса/банка) са вътрешен каталог за мапинга, не номенклатура на НАП.

## Референция

`secret/inv` и `secret/su-doxis` са образец. su-doxis има кореспонденция
„Вътрешен трансфер“ Дт 302 / Кт 304 — **нарочно не я копираме**.
`inv` печата фактура като „приемо-предавателен протокол“ към клиент
(без цени) — това е друг документ, външен, не между обекти.
